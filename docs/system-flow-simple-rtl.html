فلوی سادهٔ سیستم

هر سرویس چه کار می‌کند؟ (خیلی ساده)

کلاینت

  • کاربر را نشان می‌دهد و تغییرات او را می‌فرستد.
  • تغییر‌ها را موقتاً نشان می‌دهد قبل از ذخیرهٔ نهایی.
  • وقتی پیام دیگران می‌آید، صفحه را بروزرسانی می‌کند.

WebSocket Gateway (Go)

  • اتصال WebSocket را نگه می‌دارد و پیام‌ها را از کلاینت می‌گیرد.
  • پیام را سریعاً به دیگران پخش می‌کند و آن را به Redis می‌فرستد تا همه نمونه‌ها ببینند.
  • درخواست ذخیره‌سازی را به سرویس اسناد می‌فرستد و نتیجه را به کلاینت‌ها می‌فرستد.

Redis

  • پیام‌ها را بین گیت‌وی‌ها و سرویس‌ها پخش می‌کند (مثل کانال مرکزی).
  • اطلاعات موقت مثل «چه کسی آنلاین است» را نگه می‌دارد.

Document Service (Django)

  • ویرایش‌ها را می‌گیرد، آن‌ها را با هم ترکیب می‌کند و در پایگاه‌داده ذخیره می‌کند.
  • بعد از ذخیره، به Redis می‌گوید که تغییر انجام شده است.

PostgreSQL

  • نسخهٔ نهایی سند و تاریخچهٔ تغییرات را ذخیره می‌کند.

FastAPI و Workers (وظایف روشن)

  • FastAPI: سرویس کم‌حالت برای کارهای سریع و هماهنگ‌سازی با سرویس‌ها. - مثال‌ها: ساخت پیش‌نمایش (render)، دریافت وبهوک، تبدیل/صادرات فایل. - وقتی کار سنگین است، FastAPI یک job در صف (مثلاً Redis یا صف کاری) می‌سازد و بلافاصله یک شناسهٔ کار (job id) بازمی‌گرداند. - FastAPI می‌تواند برای اطلاعات بیشتر از Document Service درخواست بخواند و بعد از اتمام کار نتیجه را منتشر کند یا در یک مکان ذخیره (مثلاً S3) قرار دهد.
  • Workers (کارگران پس‌زمینه): - صف‌ها یا Redis streams را مصرف می‌کنند و کارهای طولانی را اجرا می‌کنند (مثلاً رندر، تولید PDF، تبدیل فرمت). - پس از اتمام، خروجی را ذخیره و نتیجه یا وضعیت را به Redis منتشر می‌کنند تا گیت‌وی یا FastAPI از آن آگاه شوند.
  • مثال جریان ساده:
    1. کاربر درخواست رندر می‌دهد → FastAPI یک job ایجاد و یک job id می‌دهد.
    2. یک Worker job را می‌گیرد، رندر را اجرا می‌کند و فایل را ذخیره می‌کند.
    3. Worker نتیجه را در Redis منتشر می‌کند یا به FastAPI اطلاع می‌دهد.
    4. Gateway یا FastAPI وضعیت را به کلاینت ارسال یا لینک فایل را منتشر می‌کنند.

فلوی ساده و مرتب (گام به گام)

  1. کاربر تغییر می‌دهد و کلاینت آن را ارسال می‌کند.
  2. گیت‌وی پیام را می‌گیرد و آن را سریع به بقیهٔ کلاینت‌ها نشان می‌دهد.
  3. گیت‌وی پیام را به Redis می‌فرستد تا همهٔ سرورها ببینند.
  4. گیت‌وی درخواست ذخیره را به Document Service می‌فرستد.
  5. Document Service تغییر را ذخیره می‌کند و به Redis خبر می‌دهد.
  6. Redis خبر را به گیت‌وی‌ها می‌رساند؛ گیت‌وی‌ها خبر را به کلاینت‌ها می‌دهند.
  7. اگر نیاز باشد، FastAPI یا workers کارهای اضافی (مثل رندر) را انجام می‌دهند و نتیجه را منتشر می‌کنند.

خلاصه: کلاینت → گیت‌وی → Redis → Document Service → Postgres → (FastAPI/Worker) → گیت‌وی → کلاینت

نکته: این تصویر یک نمای ساده‌شده است؛ جزئیات مانند احراز هویت، retryها، و format پیام‌ها در پیاده‌سازی مشخص می‌شوند.
