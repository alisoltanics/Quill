1) Project goal

This project is a simple system for editing a document in real time. That means multiple users can work on the same document and see updates.

This project is built more for learning than for shipping a production-ready product right now.

In simple words: this guide explains what each part does and how the pieces keep a shared document working.

Educational goal Learn microservice architecture, WebSocket, Redis, JWT authentication, and storing documents in a separate service.

2) Big picture

Put simply, this project is composed of a few small programs where each one has a clear job.

Here, the frontend is what the user sees in the browser, the gateway is the main entry point, the document service is the central notebook, and PostgreSQL is the storage drawer.

Frontend ←→ Gateway ←→ Document Service ←→ PostgreSQL
Frontend ←→ Auth Service ←→ Auth PostgreSQL
Document Service → Redis → Gateway → Clients

The important point is that the frontend does not talk directly to every service. Most requests go through the gateway.

Simple extra note The gateway is the middleman. If the frontend wants to read a document or verify a token, it asks the gateway, and the gateway sends the message to the correct service.

3) Services and responsibilities

Service Port Main role
frontend 3000 Show the UI, open documents, edit documents, and send user requests
gateway 8080 Main entry point for the frontend, WebSocket handling, JWT checks, and proxying some APIs
document-service 8000 Create, read, update, and delete documents and folders. Also store content and yjs_state
auth-service 8002 Register, login, refresh token, and identify users
export-service 8001 Convert document content to html, markdown, and txt
redis 6379 Broadcast messages between services
Why are services separated? Because each service has a single responsibility. This makes the system easier to understand and keeps changes in one part from affecting the others.
Simple example It is like having a kitchen, a cashier, and a guest room in separate spaces. Each one does its own job, and if something breaks, it is easier to find.

4) Databases

In the current setup, the auth service and the document service use two separate databases.

  • Document database: for documents, folders, and document versions
  • Auth database: for auth-service users
Why is this separation important? Because user data and document data are different responsibilities. Keeping them separate makes the architecture cleaner and easier to maintain over time.

In simple terms: a database is a box where data is stored. Each service has its own box so its data does not get mixed with the others.

5) Document data model

Each document has a few important pieces:

  • title: the document title
  • content: a simpler version of the content for display and fallback
  • yjs_state: the collaborative document state for Yjs

In simple learning terms: title is like the document name, content is like the plain text, and yjs_state is like a map that helps multiple people coordinate their edits together.

Why is Yjs/CRDT implemented? Because when several people edit the same document at the same time, there needs to be a way to combine everyone’s changes without breaking the text. Yjs uses CRDT so this coordination becomes simpler and more reliable.

Put simply: Yjs takes updates and merges them so all users eventually see the same synchronized text.

Why do we have both content and yjs_state? Because yjs_state is needed for live collaboration, but for some simple displays or error cases, having content helps avoid showing an empty document.

Every time a document is saved, a new version is also recorded in DocumentVersion.

6) Authentication flow

User login is done with JWT.

A JWT is like a digital pass that the frontend uses to prove the user is allowed to access something.

  1. The user logs in or registers in the frontend.
  2. The frontend sends a request to the auth-service.
  3. If the credentials are valid, two tokens are returned: access_token and refresh_token.
  4. The frontend uses the access token for API and WebSocket requests.

What happens when access token expires?

  1. If one of the requests gets a 401, the frontend tries to get a new access token using the refresh_token.
  2. If refresh succeeds, the page reloads and starts again with the new token.
  3. If refresh fails, the user is sent to the login page.
Simple note The access_token is for everyday actions. The refresh_token is only used to get a new access token.

7) Open document flow

When the user clicks a document or refreshes a document page, this path happens:

  1. The frontend reads the document ID from the URL.
  2. The frontend sends GET /api/documents/:id to the gateway.
  3. The gateway forwards the request to the document service.
  4. The document service reads the document data from the database.
  5. The response returns to the frontend.
  6. If the yjs_state is valid, it is applied in Yjs.
  7. If not, content is used as a fallback.

In other words, the frontend does not read directly from the database; it asks the gateway first, and then the gateway asks the document service.

8) Edit and sync flow

This is the most important part of the project architecture.

Current system policy Clients only update after the changes have been saved in the document service database. This means there is no direct client-to-client broadcast sync.

Full change path

  1. The user types in the editor.
  2. Yjs records the local change in the frontend.
  3. The frontend triggers autosave.
  4. The frontend sends PATCH /api/documents/:id.
  5. The gateway forwards the request to the document service.
  6. The document service saves the new content in PostgreSQL.
  7. If yjs_state exists, the document service publishes a sync-state message to Redis.
  8. The gateway, which subscribes to that channel, receives the message.
  9. The gateway broadcasts the same message to clients connected to that document.
  10. Other clients apply that state.
Edit in Browser → PATCH /api/documents/:id → Document Service Save → Redis sync-state → Gateway Broadcast → Other Clients Apply

Why was this method chosen?

Because this architecture is designed so that only data that is actually stored in the database is sent to the other clients. That means the source of truth is always the document service and its database.

Simple reminder This means that if two people type at the same time, the system makes sure the changes are saved in the main document before everyone sees them.

9) Export flow

The frontend also does not call the export-service directly for export. Like other APIs, it only calls the gateway.

  1. The user clicks Export in the frontend.
  2. The frontend sends POST /api/export?format=... to the gateway.
  3. The gateway proxies the request to the export service.
  4. The export service converts the content to the desired format.
  5. The output file returns to the browser.

The export service only handles converting the text. The browser downloads the file and shows it to the user.

Why this is useful The frontend only knows one main entry point: the gateway. This keeps the architecture cleaner and simpler.

10) Monitoring and observability

This section explains how to know if the system is healthy and where to look if something goes wrong.

Main tools

  • Prometheus: collecting metrics
  • Grafana: showing metrics on a dashboard
  • Jaeger: viewing traces
  • redis-exporter: Redis metrics
  • postgres-exporter: PostgreSQL metrics
  • node-exporter: host system metrics
What are Grafana and Prometheus? Prometheus is like an eye that collects numbers and status from services. Grafana is like a board that shows those numbers as charts and tables so we can quickly see what is wrong.

Key metrics

  • Number of WebSocket connections in the gateway
  • Number of messages received by the gateway
  • Number of successful document saves
  • Number of document save errors
  • Number of Redis publishes from the document service

Simple monitoring flow

  1. Services produce metrics.
  2. Prometheus collects those metrics.
  3. Grafana displays them.
  4. If tracing is enabled, traces go to Jaeger.
Very simple Metrics tell us where the issue is. Traces help us understand which exact path failed.

11) Current limitations

  • Because sync only happens after save, realtime feels a bit slower than direct broadcast.
  • In some cases, fallback display depends on content.
  • This is an educational project, so some security and production-level settings are intentionally kept simple.

12) Final summary

To describe the entire architecture in a few sentences:

  • The frontend shows the user interface.
  • The gateway is the main system entry point.
  • The document service is the source of truth for documents.
  • The auth service is the source of truth for users and tokens.
  • Redis is used for canonical message broadcasting.
  • Clients only update after changes are saved in the document database.
One very important sentence In this architecture, the final document version is always determined by the document service, not the client.
