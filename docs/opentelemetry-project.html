OpenTelemetry در پروژه

OpenTelemetry دقیقاً چه کمکی می‌کند؟

OpenTelemetry ابزار استاندارد برای trace و observability است. یعنی می‌توانیم مسیر اجرای یک درخواست را از یک سرویس تا سرویس دیگر دنبال کنیم.

در پروژه ما، این ابزار به ما کمک می‌کند:

  • بفهمیم درخواست از کجا شروع شده
  • ببینیم کدام سرویس کند بوده
  • کجا خطا رخ داده
  • Gateway و Document Service را در یک مسیر مشترک ببینیم
  • در Jaeger بتوانیم جریان درخواست را به صورت گرافیکی ببینیم

در پروژه ما چه بخش‌هایی tracing می‌شوند؟

ما tracing را در دو قسمت اصلی اضافه کردیم:

  • Go Gateway
  • Django Document Service

در Gateway ما برای:

  • WebSocket connection
  • incoming message processing
  • request to Document Service
  • Redis publish

span می‌سازیم.

در Django هم برای:

  • HTTP request
  • document save
  • Document/Version handling
  • general app requests

به صورت خودکار tracing فعال می‌شود.

فلوی واقعی در پروژه

Frontend
   │
   ▼
Gateway (Go)
   │  WebSocket + HTTP request
   ├─ send to Document Service
   │
   ├─ publish to Redis
   ▼
Document Service (Django)
   │
   ▼
Postgres
   │
   ▼
OTLP exporter
   │
   ▼
Jaeger UI

یعنی هر درخواست در چند بخش تقسیم می‌شود و هر بخش یک span دارد. بعد Jaeger این spans را کنار هم می‌چیند تا یک trace کامل بسازد.

چه چیزی در کد اضافه شده؟

در پروژه ما این‌ها اضافه شده‌اند:

1) Go Gateway

initTracer()
otel.SetTracerProvider(tp)

این کد یک TracerProvider می‌سازد و همه span‌ها را به OTLP exporter می‌فرستد.

2) HTTP instrumentation

mux.Handle("/ws", otelhttp.NewHandler(...))
mux.Handle("/health", otelhttp.NewHandler(...))

به این ترتیب، هر درخواست HTTP و WebSocket به‌صورت خودکار یک span دارد.

3) Message processing span

ctx, span := tracer.Start(context.Background(), "gateway.message.process")

وقتی پیام از کلاینت می‌آید، یک span مخصوص آن پیام ساخته می‌شود و در آن می‌نویسیم که آیا Redis فعال بوده و اندازه پیام چه بوده.

4) Document Service call span

ctx, span := otel.Tracer("gateway.document_service").Start(parent, "document_service.apply")

وقتی Gateway به document-service درخواست می‌فرستد، این span نشان می‌دهد که کدام اقدام برای persistence انجام شده است.

5) Django instrumentation

DjangoInstrumentor().instrument()

برای سرویس Django به‌صورت خودکار middleware و request tracing فعال می‌شود.

6) OTLP exporter

OTLPSpanExporter(endpoint=... + "/v1/traces")

این exporter span‌ها را به Jaeger ارسال می‌کند.

Jaeger چه نقشی دارد؟

Jaeger رابط بصری برای دیدن traces است.

در پروژه ما، Jaeger در Docker Compose اضافه شده:

jaeger:
  image: jaegertracing/all-in-one:1.58
  ports:
    - "16686:16686"
    - "4318:4318"

یعنی:

  • سرویس‌های ما spans را به Jaeger می‌فرستند
  • Jaeger این traces را نگه می‌دارد
  • در UI می‌توانید در مرورگر به http://localhost:16686 بروید
  • درخت trace را ببینید و بفهمید دقیقاً کجا مشکل روی داده

یک مثال واقعی از trace

Trace: request-123
  ├─ Gateway /ws span
  │   ├─ websocket message receive
  │   ├─ publish to Redis
  │   └─ call to Document Service /apply
  │
  └─ Document Service span
      ├─ request received
      ├─ document save
      ├─ version record
      └─ Redis publish

حالا اگر یکی از این مراحل کند شود، به راحتی می‌شود مشخص کرد که مشکل کجاست.

فرق tracing با metrics

OpenTelemetry / tracing Prometheus / metrics
مسیر یک درخواست را نشان می‌دهد تعداد و وضعیت عددی را نشان می‌دهد
می‌گوید کدام بخش مشکل دارد می‌گوید چند درخواست، چه CPU، چه RAM
برای debugging دقیق کاربرد دارد برای health و dashboards کاربرد دارد

پس این دو با هم مکمل هستند: یکی مسیر را نشان می‌دهد، دیگری وضعیت را.

چرا در پروژه ما لازم است؟

چون این سیستم چند سرویس دارد: Gateway، Django، Redis، Postgres. بدون tracing، پیدا کردن علت کندی یا خطا بسیار سخت است. با OpenTelemetry می‌توانیم بگوییم:

  • مشکل در Gateway بود
  • مشکل در Document Service بود
  • مشکل در DB query بود
  • مشکل در Redis publish بود

خلاصه خیلی کوتاه

OpenTelemetry در پروژه ما یعنی:

  • هر درخواست را ردیابی می‌کند
  • بخش‌های مختلف را به هم وصل می‌کند
  • به Jaeger می‌فرستد
  • به ما می‌گوید کدام سرویس و کدام مرحله مشکل دارد
