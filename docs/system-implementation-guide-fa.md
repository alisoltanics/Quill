## 1) هدف پروژه

این پروژه یک سیستم ساده برای ویرایش سند به صورت همزمان است. یعنی چند کاربر می توانند روی یک سند کار کنند و تغییرات را ببینند.

> **⚠️ این پروژه فقط برای یادگیری ساخته شده است**
> هدف این پروژه تولید یک محصول آماده بهره برداری نیست. هدف، یادگیری عمیق مفاهیم معماری میکروسرویس، طراحی سیستم، هوش مصنوعی، و مهندسی نرم‌افزار مدرن است. تمام تصمیمات طراحی با هدف یادگیری و درک بهتر الگوهای معماری انتخاب شده اند.

### موضوعاتی که در این پروژه یاد می گیرید

- **معماری میکروسرویس (Microservices Architecture)**: چگونه یک سیستم بزرگ را به سرویس‌های کوچک و مستقل تقسیم کنیم و هر سرویس مسئولیت مشخصی داشته باشد.
- **طراحی سیستم (System Design)**: یادگیری الگوهای طراحی سیستم‌های توزیع‌شده، از جمله CQRS، Event Sourcing، و Event-Driven Architecture.
- **همکاری همزمان (Real-time Collaboration)**: درک الگوهای CRDT و OT برای ویرایش همزمان چند کاربر روی یک سند.
- **WebSocket و ارتباطات بلادرنگ**: پیاده‌سازی ارتباط دوطرفه بین کلاینت و سرور با استفاده از WebSocket.
- **احراز هویت و امنیت (Auth & Security)**: پیاده‌سازی JWT، refresh token، و مدل‌های احراز هویت مدرن.
- **پیام‌رسانی با Redis Pub/Sub**: استفاده از Redis برای ارتباط بین سرویس‌ها و هماهنگی state در سیستم‌های توزیع‌شده.
- **Event Streaming با Kafka**: استفاده از Kafka برای رویدادهای غیرهمزمان و جداسازی سرویس‌ها.
- **مانیتورینگ و مشاهده‌پذیری (Observability)**: استفاده از Prometheus، Grafana، و Jaeger برای نظارت بر سیستم.
- **تست‌نویسی (Testing)**: نوشتن تست‌های واحد، یکپارچه، و سراسری برای سرویس‌های مختلف.
- **DevOps و Docker**: Containerize کردن سرویس‌ها و ارکستراسیون با Docker Compose.

به زبان ساده: اینجا قرار است بفهمیم هر قسمت چه کاری می کند و چطور این بخش ها با هم یک سند مشترک را نگه می دارند.

> **✅ هدف آموزشی پروژه**
> یاد گرفتن معماری میکروسرویس، WebSocket، Redis، احراز هویت با JWT، ذخیره سازی سند در یک سرویس جدا، Kafka، مانیتورینگ، و تست‌نویسی حرفه‌ای.

## 2) نمای کلی سیستم

اگر بخواهیم خیلی ساده بگوییم، این پروژه از چند برنامه کوچک تشکیل شده که هر کدام یک کار مشخص انجام می دهند.

در اینجا Frontend همان چیزی است که کاربر در مرورگر می بیند، Gateway مثل دروازه اصلی است، Document Service مثل دفترچه یادداشت مرکزی است و PostgreSQL مثل کشوی ذخیره سازی است.

```
Frontend ←→ Gateway ←→ Document Service ←→ PostgreSQL
```

```
Frontend ←→ Auth Service ←→ Auth PostgreSQL
```

```
Document Service → Redis → Gateway → Clients
```

پس یک نکته مهم این است که فرانت مستقیم با همه سرویس ها حرف نمی زند. بیشتر درخواست ها از Gateway رد می شوند.

> **ℹ️ بیشتر توضیح ساده**
> Gateway همان میانجی است. اگر بخواهد سند را ببیند یا توکن را بررسی کند، اول به Gateway می گوید و بعد Gateway این پیام را به سرویس درست می رساند.

## 3) سرویس ها و مسئولیت هرکدام

| سرویس | پورت | کار اصلی |
|---|---|---|
| frontend | `3000` | نمایش رابط کاربری، باز کردن سند، ویرایش سند، ارسال درخواست های کاربر |
| gateway | `8080` | ورودی اصلی سیستم برای فرانت، WebSocket، بررسی JWT، و proxy کردن بعضی APIها |
| document-service | `8000` | ساخت، خواندن، ویرایش و حذف سند و فولدر. همچنین ذخیره `content` و `yjs_state` |
| auth-service | `8002` | ثبت نام، ورود، refresh token و شناسایی کاربر |
| export-service | `8001` | تبدیل سند به `html`، `markdown` و `txt` |
| audit-service | `8003` | مصرف `document.events` از Kafka و ذخیره سابقه فعالیت سند |
| redis | `6379` | پخش پیام بین سرویس ها |

> **ℹ️ چرا سرویس ها جدا شده اند؟**
> چون هر سرویس یک مسئولیت مشخص دارد. این کار فهم سیستم را ساده تر می کند و تغییر دادن یک بخش را از بقیه جدا نگه می دارد.

## 4) پایگاه داده ها

در وضعیت فعلی، سرویس احراز هویت و سرویس سند از دو پایگاه داده جدا استفاده می کنند.

- **document database**: برای سندها، فولدرها و نسخه های سند
- **auth database**: برای کاربران سرویس احراز هویت

> **✅ چرا این جداسازی مهم است؟**
> چون داده کاربران و داده سندها دو مسئولیت مختلف هستند. جدا بودن آن ها معماری را تمیزتر می کند و در آینده نگهداری سیستم را راحت تر می کند.

## 5) مدل داده سند

هر سند چند بخش مهم دارد:

- `title`: عنوان سند
- `content`: نسخه ساده تر محتوا برای نمایش و fallback
- `yjs_state`: نسخه collaborative سند برای Yjs

یادگیری ساده: `title` مثل نام سند است، `content` مثل متن معمولی است، و `yjs_state` مثل نقشه ای است که کمک می کند چند نفر همزمان تغییرات را با هم هماهنگ کنند.

> **ℹ️ چرا Yjs/CRDT پیاده شده؟**
> چون وقتی چند نفر همزمان روی یک سند کار می کنند، باید راهی باشد که تغییرات همه را با هم ترکیب کند بدون اینکه نوشته ها خراب شود. Yjs از CRDT استفاده می کند تا این هماهنگی را ساده تر و قابل اعتمادتر کند.
>
> به زبان خیلی ساده: Yjs آپدیت ها را می گیرد و آن‌ها را با هم «مرج» می کند تا همه کاربران در نهایت یک متن هماهنگ ببینند.

> **ℹ️ چرا هم content داریم هم yjs_state؟**
> چون `yjs_state` برای همکاری همزمان لازم است، اما برای بعضی نمایش های ساده یا شرایط خطا، داشتن `content` کمک می کند که سند خالی نشان داده نشود.

هر بار که سند ذخیره می شود، یک نسخه جدید هم در `DocumentVersion` ثبت می شود.

## 6) فلو احراز هویت

ورود کاربر با JWT انجام می شود.

1. کاربر در فرانت login یا register می کند.
2. فرانت به `auth-service` درخواست می فرستد.
3. اگر اطلاعات درست باشد، دو توکن برمی گردد: `access_token` و `refresh_token`.
4. فرانت access token را برای درخواست های API و WebSocket استفاده می کند.

### وقتی access token منقضی شود چه می شود؟

1. اگر یکی از درخواست ها `401` بگیرد، فرانت تلاش می کند با `refresh_token` یک access token جدید بگیرد.
2. اگر refresh موفق باشد، صفحه reload می شود و دوباره با توکن جدید بالا می آید.
3. اگر refresh ناموفق باشد، کاربر به صفحه login فرستاده می شود.

> **⚠️ نکته ساده**
> `access_token` برای کارهای روزمره است. `refresh_token` فقط برای گرفتن access token جدید استفاده می شود.

## 7) فلو باز کردن سند

وقتی کاربر روی یک سند کلیک می کند یا صفحه را با آدرس یک سند refresh می کند، این مسیر طی می شود:

1. فرانت از URL می فهمد کدام سند باید باز شود.
2. فرانت از طریق Gateway درخواست `GET /api/documents/:id` می زند.
3. Gateway درخواست را به Document Service می رساند.
4. Document Service داده سند را از دیتابیس می خواند.
5. پاسخ به فرانت برمی گردد.
6. اگر `yjs_state` سالم باشد، روی Yjs اعمال می شود.
7. اگر نباشد، `content` به عنوان fallback استفاده می شود.

یعنی فرانت سند را مستقیم از دیتابیس نمی گیرد؛ اول Gateway می پرسد و بعد Gateway به سرویس سند می گوید.

## 8) فلو ویرایش و همگام سازی

این مهم ترین بخش معماری پروژه است.

> **⚠️ سیاست فعلی سیستم**
> کلاینت ها فقط بعد از این آپدیت می شوند که تغییرات در دیتابیس سرویس سند ذخیره شده باشد. یعنی sync مستقیم از کلاینت به بقیه کلاینت ها وجود ندارد.

### مسیر کامل تغییرات

1. کاربر در ادیتور تایپ می کند.
2. Yjs در فرانت تغییر local را ثبت می کند.
3. فرانت autosave را trigger می کند.
4. فرانت به `PATCH /api/documents/:id` درخواست می زند.
5. Gateway درخواست را به Document Service می فرستد.
6. Document Service محتوای جدید را در PostgreSQL ذخیره می کند.
7. Document Service همچنین یک event به Kafka می فرستد تا سرویس های مستقل بعد از این save، کار خود را انجام دهند.
8. اگر `yjs_state` موجود باشد، Document Service یک پیام `sync-state` روی Redis publish می کند.
9. Gateway که subscriber این کانال است، پیام را می گیرد.
10. Gateway همان پیام را به کلاینت های وصل شده به آن سند broadcast می کند.
11. کلاینت های دیگر آن state را apply می کنند.

```
Edit in Browser → PATCH /api/documents/:id → Document Service Save → Redis sync-state → Gateway Broadcast → Other Clients Apply
```

### چرا این روش انتخاب شده؟

چون در این معماری قرار است فقط داده ای به بقیه کلاینت ها برسد که واقعاً در دیتابیس ذخیره شده است. این یعنی منبع حقیقت همیشه Document Service و دیتابیس آن است.

> **ℹ️ یادآوری ساده**
> این یعنی اگر دو نفر همزمان تایپ کنند، قبل از اینکه همه ببینند، سیستم مطمئن می شود که تغییرات در سند اصلی ثبت شده باشد.

## 9) فلو کاربران آنلاین (Presence)

### ساختار داده در Redis

از یک **Sorted Set** به نام `doc:{docId}:online` استفاده می شود. هر عضو ایمیل کاربر است و score آن زمان آخرین فعالیت (Unix timestamp) است.

```
Redis Key:   doc:42:online
Members:     ["ali@example.com", "sara@example.com"]
Scores:      [1693584000000, 1693584005000]
```

### مسیر کامل

1. کاربر WebSocket باز می کند. Gateway ایمیل را از JWT استخراج می کند.
2. وقتی کلاینت پیام `join` می فرستد، Gateway با `ZADD` ایمیل کاربر را به Sorted Set اضافه می کند.
3. Gateway لیست کامل کاربران آنلاین را از Redis می خواند.
4. Gateway یک پیام `presence-update` شامل لیست کامل کاربران روی کانال `gateway:events` Redis publish می کند.
5. همه نمونه‌های Gateway این پیام را دریافت و به کلاینت‌های متصل broadcast می کنند.
6. فرانت لیست کاربران آنلاین را دریافت و نمایش می دهد.

```
Client Join → Gateway ZADD Redis → Gateway Get Full List → Publish presence-update → All Gateways Broadcast → Frontend Displays
```

### پاکسازی خودکار

هر عضو TTL برابر ۹۰ ثانیه دارد. اگر کاربری قطع شود (مثلاً بستن مرورگر)، تا ۹۰ ثانیه بعد از لیست حذف می شود. همچنین قبل از خواندن لیست، entries منقضی شده با `ZREMRANGEBYSCORE` پاک می شوند.

### قطع ارتباط کاربر

1. وقتی WebSocket بسته شود، `readPump` متوجه می شود.
2. Gateway با `ZREM` ایمیل کاربر را از Sorted Set حذف می کند.
3. لیست به روز شده publish و به همه کلاینت ها broadcast می شود.

> **ℹ️ چرا Sorted Set؟**
> Sorted Set به ما امکان می دهد هم لیست کاربران را سریع بخوانیم (`ZRANGE`)، هم ورودی های قدیمی را پاک کنیم (`ZREMRANGEBYSCORE`)، و هم اگر Gateway کرش کرد، entries خودکار منقضی شوند.

## 10) نشانگرهای از راه دور (Remote Cursors)

هر کاربر می تواند نشانگر (cursor) کاربران دیگر را به صورت زنده در سند ببیند. رنگ نشانگر بر اساس ایمیل کاربر تعیین می شود و با hover روی نشانگر، ایمیل کاربر نمایش داده می شود.

### ارسال موقعیت نشانگر

1. فرانت هر بار که کاربر تایپ می کند یا جای مکان‌نما را تغییر می دهد، یک پیام `cursor-update` با ساختار `{email, position}` ارسال می کند.
2. فرانت ارسال را با debounce ۳۰ میلی‌ثانیه محدود می کند تا پیام های اضافی ارسال نشود.
3. Gateway پیام را روی کانال Redis `gateway:events` publish می کند تا همه نمونه‌های Gateway آن را دریافت کنند.

### دریافت و نمایش

1. فرانت پیام `cursor-update` را از Gateway دریافت می کند.
2. لیست نشانگرهای فعال (`remoteCursors`) به روز می شود.
3. یک پلاگین ProseMirror به نام `RemoteCursorsExtension` این لیست را دریافت کرده و برای هر کاربر یک `Decoration.widget` در موقعیت مناسب ایجاد می کند.
4. رنگ نشانگر از روی هش ایمیل کاربر تولید می شود تا هر کاربر رنگ ثابتی داشته باشد.

> **ℹ️ چرا rebuild در هر تراکنش؟**
> ویرایشگر TipTap از Yjs برای همگام سازی استفاده می کند. وقتی کاربر تایپ می کند، Yjs تراکنشی ایجاد می کند که محتوای سند را کامل جایگزین می کند. اگر از `DecorationSet.map` استفاده کنیم، موقعیت های نشانگر نادرست شده و نشانگرها ناپدید می شوند. به همین دلیل در هر تراکنش، نشانگرها بر اساس موقعیت جدید سند بازسازی می شوند.

### فلو کلی

```
User Types → Send cursor-update (30ms debounce) → Gateway Publish Redis → All Gateways Broadcast → Frontend Updates Plugin State → Rebuild Decorations
```

## 11) سرویس Audit و Kafka

بعد از اینکه Document Service تغییرات را در PostgreSQL ذخیره می کند، یک event مستقل به Kafka منتشر می کند.

این event به شکل یک پیام `document.updated` ارسال می شود و شامل شناسه سند، شناسه کاربر، نسخه، timestamp و شناسه کلاینت است.

سرویس Audit به صورت مستقل این topic را مصرف می کند و هر رویداد ذخیره شده را در جدول `audit_activity` ثبت می کند.

- Kafka topic: `document.events`
- سرویس Audit: `/api/documents/:id/activity`
- ذخیره activity به شکل ORM با SQLAlchemy

> **ℹ️ چرا Kafka؟**
> Kafka به سرویس های downstream اجازه می دهد بدون وابستگی مستقیم به Document Service، رویدادهای persistence را مصرف کنند.

## 12) فلو اکسپورت

فرانت برای اکسپورت هم مستقیم سراغ export-service نمی رود. مثل بقیه APIها فقط Gateway را صدا می زند.

1. کاربر در فرانت روی Export کلیک می کند.
2. فرانت به `POST /api/export?format=...` روی Gateway درخواست می زند.
3. Gateway درخواست را به Export Service proxy می کند.
4. Export Service محتوا را به فرمت دلخواه تبدیل می کند.
5. فایل خروجی به مرورگر برمی گردد.

Export Service فقط نقش تبدیل متن را دارد. خود مرورگر این فایل را دانلود می کند و آن را در سیستم کاربر نشان می دهد.

> **✅ مزیت این کار**
> فرانت فقط یک درگاه اصلی می شناسد: Gateway. این کار معماری را تمیزتر و ساده تر می کند.

---

## 13) مانیتورینگ و مشاهده پذیری

این بخش برای این است که بفهمیم سیستم سالم است یا نه، و اگر مشکلی پیش آمد، از کجا باید دنبال علت بگردیم.

### ابزارهای اصلی

- **Prometheus**: جمع کردن متریک ها
- **Grafana**: نمایش متریک ها روی داشبورد
- **Jaeger**: دیدن traceها
- **redis-exporter**: متریک های Redis
- **postgres-exporter**: متریک های PostgreSQL
- **node-exporter**: متریک های سیستم میزبان

> **ℹ️ Grafana و Prometheus یعنی چی؟**
> Prometheus مثل یک چشم است که اعداد و وضعیت سرویس ها را جمع می کند. Grafana مثل یک تابلو است که این اعداد را به صورت نمودار و جدول نشان می دهد تا سریع ببینیم چه چیزی درست نیست.

### متریک های مهم

- تعداد اتصال های WebSocket در Gateway
- تعداد پیام های دریافتی Gateway
- تعداد ذخیره های موفق سند
- تعداد خطاهای ذخیره سند
- تعداد publishهای Redis از سمت Document Service

### فلو ساده مانیتورینگ

1. سرویس ها متریک تولید می کنند.
2. Prometheus این متریک ها را جمع می کند.
3. Grafana آن ها را نمایش می دهد.
4. اگر tracing فعال باشد، traceها به Jaeger می روند.

> **ℹ️ خیلی ساده**
> متریک ها می گویند کجا مشکل داریم. traceها بیشتر کمک می کنند بفهمیم مشکل دقیقاً در کدام مسیر اتفاق افتاد.

---

## 14) محدودیت های فعلی

- چون sync فقط بعد از save انجام می شود، realtime کمی کندتر از حالت broadcast مستقیم است.
- در بعضی حالت ها نمایش fallback به `content` وابسته است.
- این پروژه آموزشی است، پس بعضی تنظیمات امنیتی و production-level هنوز ساده نگه داشته شده اند.

---

## 15) خلاصه نهایی

اگر بخواهیم کل معماری را در چند جمله بگوییم:

- فرانت رابط کاربری را نمایش می دهد.
- Gateway درگاه اصلی سیستم است.
- Document Service منبع حقیقت برای سندها است.
- Auth Service منبع حقیقت برای کاربران و توکن ها است.
- Redis برای پخش پیام canonical استفاده می شود.
- کلاینت ها فقط بعد از ذخیره شدن تغییرات در دیتابیس سند، آپدیت می شوند.

> **✅ یک جمله خیلی مهم**
> در این معماری، نسخه نهایی سند را همیشه Document Service تعیین می کند، نه خود کلاینت.
