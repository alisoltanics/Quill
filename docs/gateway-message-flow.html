چرخهٔ پیام در Gateway — خلاصهٔ فلو

  1. کلاینت (مرورگر) روی Save کلیک می‌کند و محتوای کامل سند را از طریق WebSocket به Gateway می‌فرستد ({clientId, text, full: true}).
  2. Gateway پیام را دریافت کرده و آن را به کانال Redis منتشر می‌کند: PUBLISH gateway:events (الگوی publish-only وقتی Redis فعال است).
  3. تمام نمونه‌های Gateway که به Redis سابسکرایب هستند پیام را دریافت می‌کنند و آن را به hub.broadcast می‌دهند تا به کلاینت‌های محلی پخش شود.
  4. Gateway به Document Service درخواست POST /apply می‌فرستد تا محتوا در PostgreSQL ذخیره و یک رکورد در DocumentVersion ثبت شود؛ Document Service پس از ذخیره نتیجه را به Redis منتشر می‌کند.
  5. کلاینت‌ها از طریق WebSocket پیام ذخیره‌شده را دریافت کرده و ویرایشگر محلی را با مقدار سرور همگام می‌کنند. برای بارگذاری مجدد صفحه، فرانت‌اند می‌تواند GET /document روی Gateway را بخواند (Gateway از Document Service پروکسی می‌کند).

اگر کلاینت از WebSocket آپدیت می‌گیرد، چرا باز هم از Redis استفاده می‌کنیم؟

پاسخ کوتاه: کلاینت‌ها آپدیت‌ها را از طریق WebSocket از همان Gateway که به آن وصل‌اند دریافت می‌کنند، اما Redis برای توزیع پیام‌ها بین نمونه‌های مختلف Gateway و برای دریافت پیام‌های منتشرشده از سرویس اسناد ضروری است.

  • توزیع بین نمونه‌ها: وقتی چندین instance از Gateway اجرا می‌شوند، یک بروزرسانی ساخته‌شده در یکی از آنها باید به بقیه برسد تا همهٔ کلاینت‌ها در همهٔ نمونه‌ها همگام شوند؛ Redis pub/sub این توزیع را ساده می‌کند.
  • دریافت پیام از Document Service: زمانی که Document Service پس از ذخیره محتوا پیام منتشر می‌کند، Redis کانالی است که همهٔ Gatewayها روی آن سابسکرایب می‌کنند تا پیام ذخیره‌شده را دریافت و به کلاینت‌های محلی بفرستند.
  • تفکیک وظایف و کنترل: Gateway نقطهٔ ورود امن برای مرورگرها است (احراز هویت، نرخ‌دهی، لاگ) و Redis نقشِ لایهٔ انتقال رویداد را دارد؛ این جداسازی امن‌تر و قابل‌نگهداری‌تر است.
  • قابلیت ارتقا: اگر نیاز به دوام و بازپخش پیام‌ها داشته باشی، می‌توانی Redis Streams یا Kafka اضافه کنی بدون اینکه تغییر زیادی در منطق WebSocket کلاینت‌ها ایجاد شود.

توضیح مفصل: نقش Redis بین چند Gateway (نمونهٔ اضافه‌شدهٔ شما)

در معماری فعلی شما، Redis بیشتر برای هماهنگ‌کردن چند نمونهٔ Gateway با یکدیگر استفاده شده، نه برای ذخیرهٔ دائمی سند. متن زیر را به‌صورت ساده‌شده اضافه کردم تا این نکته واضح‌تر باشد:


            ┌── Gateway #1 ── Browser A
  Browser ──────┤
            ├── Gateway #2 ── Browser B
            └── Gateway #3 ── Browser C
                  │
                Redis

فرض کن Browser A به Gateway #1 وصل است و تغییرش را ارسال می‌کند. اگر Redis نباشد، Gateway #1 فقط کلاینت‌های متصل به خودش را می‌بیند؛ Gateway #2 و #3 از آن بی‌خبر می‌مانند.

Redis به‌عنوان Message Broker / Pub/Sub این وسط قرار می‌گیرد:


  Browser A
    │
    ▼
  Gateway #1
    │
    │ PUBLISH
    ▼
  Redis ───────────────┐
    │                 │
    ▼                 ▼
  Gateway #2       Gateway #3
    │                 │
    ▼                 ▼
  Browser B         Browser C

پس چرا Redis؟

  1. Broadcast بین چند Gateway: مهم‌ترین دلیل همین است — وقتی Gatewayها stateless و قابل scale باشند، Redis تضمین می‌کند که یک رویداد تولیدشده در یک instance به همهٔ instanceهای دیگر برسد.
  2. جلوگیری از وابستگی کلاینت‌ها به یک Gateway خاص: کاربران را مجبور نمی‌کند که همیشه به یک نمونهٔ خاص وصل بمانند؛ اگر کاربر A به Gateway #1 وصل باشد و B به Gateway #2، وقتی A تغییری ذخیره می‌کند، B هم آن را می‌بیند.
  3. Redis دیتابیس اصلی نیست: در این فلو، مسئولیت ذخیرهٔ دائمی با Document Service و PostgreSQL است. Redis فقط برای توزیع realtime eventها استفاده می‌شود؛ اگر Redis پاک شود، داده‌های اصلی در PostgreSQL امن می‌مانند.

نکته دربارهٔ دوام پیام‌ها (durability)

Redis pub/sub یک صف durable نیست: اگر subscriber در لحظهٔ انتشار آفلاین باشد، پیام از بین می‌رود. بنابراین:

  • برای fan-out و realtime UI، pub/sub ساده و کم‌تاخیر مناسب است.
  • اگر به بازپخش، دوام یا پردازش تضمین‌شده نیاز داری، به Redis Streams یا Kafka فکر کن.
